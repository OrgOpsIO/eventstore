### Persisted folds

- **Persisted folds: a cold process folds only what is new.** A second tier behind the context cache keeps a fold's state in the store, beside the events, with the settled cursor it was folded up to; a fresh process (a deploy, a new container) starts from it and reads and folds only the delta. On when both hold: the store has `persistedFolds: true` (`new MemoryStore({ schema, persistedFolds: true })`, `configure({ postgres: { persistedFolds: true } })`, `printSchemaSql(schema, { persistedFolds: true })`) and the fold has an identity:

  ```ts
  const ledgerStats = defineFold({ name: "ledger-stats", version: 1, fold: ledger.$foldBy<string, { count: number }>((e) => e.data.category, { EntryBooked: (d, s) => ({ count: (s?.count ?? 0) + 1 }) }) });
  await es.context({ query, fold: ledgerStats, initial: () => new Map() });
  ```

  A cache of your fold, never a second source of truth: the delta and the context version still come from the store on every load, so `appendIf` decides as before. Only settled events are stored. A version bump is another state, folded from zero. States are encoded with `node:v8` (Map, Set, Date, bigint survive; a class instance, a function, a null-prototype object, an own property on a Map, Set or Date, a non-enumerable property or a getter is not stored and reported, as is a state too deep to encode); a shared-instance `initial` (`new Map()` instead of `() => new Map()`) throws with the fix. A state is written once `contextCache.persist.after` settled events (default 500) were folded since the last read or write, awaited, as a monotone upsert; a failed write is reported, never thrown; a failed read fails the load. Postgres: table `<table>_fold_state` (application role: `SELECT, INSERT, UPDATE`), under `rls` its own policy on `app.current_tenant` that also excludes the empty tenant, reached only through tenant views. `onLoad` gains `start` (`"cache"`, `"stored"`, `"initial"`) and `stored` (`readMs`, `written`, `writeMs`, `error`). New: `defineFold`, `DefinedFold`, `FoldIdentity`, `FoldStateStore`, `FoldStateKey`, `StoredFoldState`, `contextCache.persist`. Measured (`sh bench/persisted-fold.sh matrix`, stage 7, `bench/RESULTS.md` S2), a cold load in a fresh process on Postgres 18, median of 11: 10 000 events of 1 KB 76.9 ms folding from zero vs. 5.85 ms from the persisted fold (8.28 ms with 100 new events), 13×; 100 000 events: see "Measured" above; 10 000 events of 200 KB 10.6 s vs. 4.8 ms. Warm loads unchanged (~1 ms on a loaded machine). Below ~100 events it does not pay: at 100 × 1 KB the stored state's read made a load with 10 new events slower (0.85×). A stored state costs its size to read: ~8 ms at 570 KB, ~78 ms at 5.7 MB plus ~5 ms to size it (`bench/RESULTS.md`, "What the tier itself costs").

### Live read models

- **Live read models: one fold per key, kept in memory, read without folding.** `defineReadModel({ name, version, source, keyBy, fold, initial, batchSize?, onFailedKey? })` declares one; `es.forTenant(t).readModel(definition)` keeps it live in the process — one model per tenant, name and version, fed by one `subscribe` whose cursor lives in memory only (nothing is written to the database; after a restart it rebuilds from the store). `keyBy` is a scope key: an event's key is its scope value, as in queries.

  ```ts
  const offers = defineReadModel({ name: "offers", version: 1, source: sales.$filter(), keyBy: "offerId", initial: { status: "draft" }, fold: sales.$fold<{ status: string }>({ OfferMade: (_, s) => ({ ...s, status: "open" }) }) });
  const model = es.forTenant(t).readModel(offers);
  const offer = await model.get(offerId, { atLeast: { transactionId: appended.transactionId, sequence: appended.last } });
  ```

  A cache of your fold, never a second source of truth: `model.get(k)` equals `es.context({ query: source ∧ keyBy = k, fold, initial }).state` for every key (a property test on the memory store and on Postgres with concurrent writers), and the model hands out no context, so commands still decide on the store. `get(key)` reads memory and folds 0 events; it waits for the first rebuild and, with `atLeast`, for a read-your-writes token, both bounded by `timeoutMs` (default 10 s, then `TransientError` with code `read_model_timeout`). `list({ where, sort, offset, limit })`: equality on top-level state fields (AND), one sort with a fixed order (numbers < strings < booleans < Dates, missing last, ties by key), offset paging, `total`, `failed`, `revision`; a result is kept per shape until the model changes. **Push on change:** `model.watch(key, onState)` delivers the current state, then the new state after every folded page that changed it; `model.watchList({ where }, onChange)` delivers `{ revision, rows, removed }`. Each event is folded once, by the feed, however many watch; model watchers have `es.watch`'s guarantees and share its limits (`watch.maxWatchers`, `watch.maxPendingBatches` → `WatchOverflowError`, `signal`, `onError` once), a tenant view's model reads that tenant only, and an append in another process reaches a watcher through the doorbell (`postgres: { live: true }`; measured in the test with two OS processes: 29 ms). **A fold that throws on one event** skips that event only (stage-2 bisection): every other key goes on, the event's key becomes failed — `get` throws the new `FailedKeyError` (model, key, event type, id, sequence and transaction id, never the payload; the fold's error as `cause`), `list` leaves it out, its watchers end with `onError`, `onFailedKey` is called once; fold on read throws for that key too. Fix the fold and bump the version. `model.status`: `phase`, `cursor`, `keys`, `failed`, `folded`, `foldMs`, `revision`. `model.stop()`; `es.close()` stops every model. `invalidate()` on a view rebuilds that view's live read models in place (see "`invalidate()` on a view" below); erasing a tenant rebuilds every live model holding it, the root view's included (README, "Erasing a tenant", steps 3 and 4). A past view (`asOf`) refuses; under `rls` the root view's model fails with the store's `UsageError`. New: `defineReadModel`, `ReadModelDefinition`, `LiveReadModel`, `ReadModelReadOptions`, `ListOptions`, `ListRow`, `ListResult`, `ListChange`, `ReadModelWatchOptions`, `ReadModelStatus`, `FailedKeyError`. **Type-level addition (breaking for code that implements `EventStoreApi`):** `EventStoreApi` gains `readModel`; code that implements `EventStoreApi` itself must add it. `WatchLimits.maxWatchers` now counts read model watchers too. Benchmarks of live vs. fold on read: `bench/RESULTS.md`.

### Persisted read models

- **Persisted read models: the same definition, kept as rows plus a checkpoint in the store.** `es.forTenant(t).persistedReadModel(definition)` takes a `defineReadModel` definition and keeps its states in the store — one row per key and one checkpoint per model, written in the same transaction — so it resumes after a restart at the checkpoint, folds only what came after it, and never applies an event twice. On only when the store has `persistedModels: true` (`new MemoryStore({ schema, persistedModels: true })`, `configure({ postgres: { persistedModels: true } })`, `printSchemaSql(schema, { persistedModels: true })`); without it the handle fails with a `UsageError` and nothing is created.

  ```ts
  const model = es.forTenant(t).persistedReadModel(offers);
  const offer = await model.get(offerId); // the stored row + the key's events beyond it: current without waiting
  const page = await model.list({ where: { status: "open" }, atLeast: { transactionId: appended.transactionId, sequence: appended.last } });
  ```

  A cache of your fold, never a second source of truth: `get(k)` equals `es.context({ query: source ∧ keyBy = k, fold, initial }).state` for every key, or both throw — a property test on the memory store and on Postgres with concurrent writers, compared without waiting, also while the writer lags — and the handle hands out no context. `get(key)` is the key's row plus its events beyond it from the store (Marten's `FetchLatest`), through an in-process copy that moves forward, so a warm `get` folds 0 events and a cold one only the key's events beyond the model's checkpoint (row and checkpoint read in one snapshot, so events that left the state unchanged are never folded again); it takes no options. `list(...)` reads the rows: as current as the checkpoint; `atLeast` waits for a token, decided from the store in any process; the live model's query surface and order over the state's JSON-representable top-level fields (anything else counts as missing); `total`, `failed`, `revision` and the page from one snapshot. `watch(key)` and `watchList({ where })` as on the live model, fed by the writer's committed rows, in every process with a handle (a notification in the page transaction; with `live: true` measured 32–33 ms from an append in one OS process through the writer in a second to a watcher in a third, test `persisted-model-postgres.test.ts`); `removed` may name a key that changed twice within one notification. **One writer per model and version**: a session advisory lock keyed by the events table, tenant, name and version, on one extra connection per store and process (TCP keepalives set; one statement at a time), an epoch claimed by every new writer and checked in every page transaction, so a writer that lost its lock unnoticed is fenced at its next page; every other process is a standby that reads and takes over (tested with two writer processes, one `SIGKILL`ed or its lock session terminated half-way through 800 events: every key equal to fold on read, each event applied once). At most 1 000 writer locks per store and process. A fold that throws on one event fails that key with a failed marker in its row (the dead letter: type, id, sequence, transaction, error message — at most 1 000 UTF-16 units, a character never split, NUL and lone surrogates as U+FFFD — never the payload); `get` throws `FailedKeyError` in every process, `onFailedKey` runs once in the writer's; a database error is retried and never skips an event; a fold result that is not storable fails its key the same way. `status()`: `phase`, `role`, `checkpoint`, `epoch`, `revision`, `failed`, `lag { events, ms }` (`events` counted up to 1 000, beyond an upper bound that holds under transaction/sequence inversion), `folded`, `foldMs`, `readFolded`. Postgres: tables `<table>_read_model` and `<table>_read_model_state` (application role: `SELECT, INSERT, UPDATE` on both; under `rls` a policy each on `app.current_tenant`, the root view's handle fails). New: `EventStoreApi.persistedReadModel` (and on `es`), `PersistedReadModel`, `PersistedReadModelStatus`, the store option `persistedModels` (memory and Postgres, and `printSchemaSql`). **Type-level addition (breaking for code that implements `EventStoreApi`):** `EventStoreApi` gains `persistedReadModel`; code that implements `EventStoreApi` itself must add it. **Changed (unreleased) live read model order:** `list` now orders strings and the key tie-breaker by Unicode code point instead of UTF-16 code unit (they differ only where a character above U+FFFF meets U+E000–U+FFFF), and `±Infinity` counts as missing like `NaN`, so live and persisted lists agree. Erasing a tenant now also covers the two tables (README, "Erasing a tenant"). Benchmarks of persisted vs. live vs. fold on read: `bench/RESULTS.md`.

### Versions and rebuild

- **Versions and rebuild: a bump builds the new version beside the old one, which keeps answering until the new one has caught up.** For a persisted read model, a version opened while another version of the name is active in the tenant is `building` (new `PersistedReadModelStatus.building`): it builds into its own rows, its `get` answers at once (row + delta, current, for every key: a delta of more than `contextCache.maxEvents` events beyond the new version's checkpoint — early in a build, a key's whole history — is folded in pages of `maxEvents`, as every persisted `get` does, so a bump never makes a key unreadable and never throws `ContextTooLargeError`), its `list` waits until it has switched (bounded by `timeoutMs`, then `TransientError` `read_model_timeout` naming the build), and its `watch` / `watchList` registrations wait too, so no build page reaches a client. Its own writer switches it (`building` → `active`, one transaction that rings every process) once its feed has passed the newest event of its source as of the moment it began building — not on `lag.events === 0`, which a model under steady writes rarely shows. Nothing happens to the old version at the switch: each process reads the version its code knows, so a rolling deploy needs nothing more. A first version, or one with nothing active beside it, is `active` from the start (stage-4 behaviour). **Retiring** is an operator's recipe in the README ("Retiring an old version"): one transaction marks the versions below an active one `retired` and deletes their state rows, keeping the model row as a tombstone — a straggler of the old code fails with a `UsageError` at its next page, claim, cold `get`, `list` or `status()` and never rebuilds the old version or serves an empty `list`. New columns `status` and `fingerprint` in `<table>_read_model` and `fingerprint` in `<table>_fold_state` (in `printSchemaSql` with the existing options): **reinstall a database installed by an earlier unreleased build of this branch.**
- **A persisted fold's context over `maxEvents` loads, in pages.** With the persisted fold tier on, a load whose delta exceeds `contextCache.maxEvents` folds it a page of `maxEvents` settled events at a time and writes the state after each page, instead of throwing `ContextTooLargeError` — so a version bump no longer makes a large context unreadable for good, and the next load starts from the last page. The answer and its context version for `appendIf` are the unpaged fold's; `maxEvents` then bounds a page, not the context. Without the tier nothing changes. A bump refolds each context once, on its first load in new code; the README has a `DELETE` recipe for old versions' rows.
- **A forgotten version bump warns.** A fingerprint of the fold — a hash of its handlers' own source text (through `defineFold`, `$fold` and `$foldBy`), and for a read model also its source, `keyBy` and initial state, plus the JSON schema and upcaster of every event type it reads — is stored beside the version (the persisted model's writer claims with it; a persisted fold writes it with every state; new optional `StoredFoldState.fingerprint` for store implementers). A process whose fold has another fingerprint under the same version warns once per process and version: `process.emitWarning(…, { type: "EventStoreWarning", code: "ES_FOLD_CHANGED" })`, one stderr line, routable with `process.on("warning")`, silenced by `--no-warnings`. It only warns — the version stays the only signal; it cannot see imported helpers or captured values, and another build of the same code may warn once. A `ContextCache` constructed by hand knows no event schemas, so it writes and compares no fingerprint (no false warning between it and a runtime sharing a fold).
- **A live read model may start from a persisted state.** `es.readModel(definition, { start: "persisted" })` (new type `LiveReadModelOptions`) loads the persisted model of the same name and version — every row and its checkpoint in one `REPEATABLE READ` snapshot — and folds only what came after it, instead of replaying the source; failed rows become failed keys (without calling `onFailedKey` again). Nothing to start from (no rows, no checkpoint, a retired version, an undecodable row) falls back to the rebuild; a store without `persistedModels` fails the model with a `UsageError`. **Breaking for code that implements `EventStoreApi`:** `EventStoreApi.readModel` gains this optional parameter (code that implements `EventStoreApi` must accept it).

  ```ts
  const live = es.forTenant(t).readModel(offers, { start: "persisted" });
  const offer = await live.get(offerId); // the persisted rows, then only the events beyond their checkpoint
  const status = (await es.forTenant(t).persistedReadModel(offers).status()).building; // a new version still building beside the old one?
  ```

### Tenants, RLS and erasure

- **One processor for every tenant: a persisted read model defined with `processor: "cross-tenant"` has one writer for all tenants.** New optional `ReadModelDefinition.processor` (validated by `defineReadModel`, part of the fingerprint only when set, so existing definitions hash as before). The root view's handle (`es.persistedReadModel(def)`) is the processor: it elects like any writer, runs one subscription over the whole source and writes, per page and in one transaction, each tenant's state rows and model row — the rows a per-tenant writer would leave — plus a processor row (tenant `''`, its epoch and checkpoint over every tenant, no fact). Every `es.forTenant(t).persistedReadModel(def)` is a reader: it never locks or subscribes (`role` always `"standby"`), and its `get`, `list`, `watch`, `watchList` and `status()` are the per-tenant ones on its own rows; the processor notifies each tenant it wrote. The processor's `get`/`list`/`watch`/`watchList` reject with `UsageError`; it needs `configure({ tenant })`. A per-tenant writer of the same name and version (old code in a deploy) stays exactly-once beside it (both lock the tenant row and apply only the events beyond its checkpoint — the test's mutation without that filter applies every event twice). Blue-green and the switch work across tenants (every tenant with any version of the name gets an active row of the new version at the switch, also one without events in the new source), with a cross-tenant retire recipe in the README. A poison event fails its key in its tenant; `onFailedKey` gets the new **`FailedKeyError.tenant`**. Measured in `tenants-postgres.test.ts`: one append to one tenant costs the processor 18 statements with readers open in 1 and in 10 tenants alike, and the readers none. What it costs (`bench/RESULTS.md` "Stage 6"): a rebuild is one feed, 4.0–5.6× as long as 100 per-tenant writers at 100 tenants; and while the state table's statistics do not know a new model's rows, a page with 1 000 tenants spends most of its time reading them (211.5 ms of 247 ms) — the README advises `ANALYZE` once a build has written its first pages.

  ```ts
  const offersAll = defineReadModel({ ...offers, processor: "cross-tenant" });
  const processor = es.persistedReadModel(offersAll);                       // the one writer (elects; standbys take over)
  const page = await es.forTenant(t).persistedReadModel(offersAll).list({ where: { status: "open" } }); // a reader
  ```

- **Under `rls`, the processor runs as its own role: `postgres.processorRole`.** With `rls: true` and `persistedModels: true`, the new store option `processorRole` (also on `printSchemaSql`) makes the installer create three policies **`TO` that role only** — read every tenant's events; read and write every tenant's model rows and state rows (never a state row of the empty tenant) — and none on the fold states; the application role's policies and isolation are unchanged. The store reads `current_user` once: only a store connected as that role may read every tenant at its root (`query`, `statistics`, subscriptions) and run a cross-tenant processor; its appends and per-tenant models at the root stay refused, and every other connection is refused as before. Without `rls` or `persistedModels`, or with a name that is not an identifier, `processorRole` is a `UsageError`. A policy whose role or expression drifted is recreated; a store installing without the option leaves existing processor policies and names them in `warnings()`; the adopt check counts the read policy as the store's own. README "Roles for RLS": the grants, and **never grant the processor role to the application role** (members inherit its policies). Tested under `rls` with a non-superuser table owner bound by `FORCE`, a non-owner application role and the processor role: in a tenant's session the application role sees only that tenant's fold states, model rows and state rows — never another tenant's, never the processor row, nothing with the reset value `''` — and cannot write another tenant's; the processor role sees every tenant and cannot append.
- **Erasing a tenant covers every kept state, also with a cross-tenant processor running.** The README recipe "Erasing a tenant" is rewritten as steps with one SQL block: the **erasure lock** first (`pg_advisory_xact_lock(hashtext('eventstore:erasure'), hashtext('<schema>.<table>'))`), `set_config` under `rls`, then the `DELETE`s of events, fold states, model state rows and model rows of the tenant in one transaction, with a **row-count check** against `statistics()` before `COMMIT` (a missing `set_config` under `FORCE` deletes 0 rows silently). Every cross-tenant page takes that lock shared and checks that its events still exist (else it rolls back with the internal `TransientError` `read_model_page_stale` and reads again), so a page read before an erasure never writes the erased tenant back, and one in flight finishes before the erasure deletes. A cross-tenant version switch takes the lock shared too, so it never gives the erased tenant a model row of the new version. Tested with the recipe as printed under `rls`, the processor paused before its page, inside its page and not at all, and with a version switch started inside the open erasure: 0 rows of the erased tenant in the four tables, no answer from memory, the other tenant unchanged; without the count check, or without the recipe's lock line, the tenant's rows came back (the tests' mutation checks), and without the switch's lock its new model row survived the erasure.
- **`invalidate()` on a view now also rebuilds that view's live read models and drops its persisted handles' `get` copies.** Without a query, `es.forTenant(t).invalidate()` (and on any view) forgets the cached contexts as before, **rebuilds each live read model of the view in place** — the same handle: reads issued meanwhile wait for the rebuild, `revision` only grows, `start: "persisted"` re-reads the persisted rows — and ends its watchers with `TransientError` code **`read_model_rebuilt`** (open them again); a failed or stopped model stays so. It drops the `get` copies of the view's persisted handles, which keep running. `invalidate(query)` still only forgets that query's contexts, and dropping a tenant view from the `maxTenantViews` memo releases its cache only. Before, a running live model kept answering an erased tenant's facts until it was stopped and declared again (recipe step 3 said so); that still works.

### Subscriptions

- **Read your writes: an append returns its transaction, a subscriber says whether it has passed it.** `AppendResult.transactionId` (also on `appendIf` and `command()`'s `appended`) is the transaction id every record of the batch carries; `{ transactionId: appended.transactionId, sequence: appended.last }` is the token. `Subscription.hasPassed(token)` is `true` once the subscription handled or skipped it — by its cursor, or by `Subscription.watermark`, the snapshot horizon of its last empty page, for a write its query does not match. New `QueryResult.watermark?`: Postgres returns the `xmin` of the read's own snapshot (one more output column of the read, taken from that very statement — a separate read of the horizon afterwards is not sound), the memory store returns one only without `transactions` hooks. The append function stays `es_append_if_v5`: the id is one more output column of the append statement, so no DDL and no `install: "none"` rerun. Both columns cost nothing measurable: a single-event append took 0.438 ms before and 0.431 ms after, and an empty subscriber page 0.360 ms before and 0.366 ms after. A token is passed about 27 ms after the append with the doorbell (`live: true`) and within the 500 ms poll without it (`sh bench/subscriptions.sh`, numbers in `bench/RESULTS.md`). **Breaking for custom `EventStore` implementations**: `append` and `appendIf` must return `transactionId` (the type says so). `subscribe` now refuses a `batchSize` that is not a positive integer with `UsageError`: `0` used to be accepted and read only empty pages, never delivering, and their watermark would have reported unread events as passed. `query({ limit: 0 })` is unchanged.
- **`"skip"` skips the one poison event, not the batch.** Until now `onError` → `"skip"` advanced past the whole failed batch: with the default `batchSize` of 500, one bad event dropped up to 499 good ones. The failed batch is now split in halves, left to right, every part that succeeds is committed, and `onError` is asked once more with the single event that fails alone (`"skip"` it, `"retry"`, or `"stop"`). Behaviour change for `batchSize > 1` only; with `batchSize: 1` nothing changes. Neighbours of a failed batch are delivered again (at-least-once). Measured on a page of 500 with one poison event: 17–19 handler calls instead of 1, and 499 events applied. In processor mode on Postgres, with a transaction per call and the locking target of the README, the page took 26–39 ms (medians of three runs of 11) instead of 2.0–3.2 ms (`node bench/subscriptions-bench.mjs poison 11`).
- **Processor mode: `subscribe(…, { target })`.** A `CheckpointTarget` (`load()`, `skip(event, error)`) keeps the checkpoint in the target's own store: in one transaction the handler locks its checkpoint row, applies only the events beyond it and moves it to `cursorOf(events)` (README, "Processor mode"); nothing is saved after the handler, a skipped event goes to `target.skip` (with a dead letter if you keep one, under the same lock), and `Subscription.cursor` is what the target committed. A failed save after a committed handler can no longer apply a batch twice. The subscription stays at-least-once, and a redelivered batch can be longer than the one already committed (a lost COMMIT acknowledgement with new events before the retry, or two subscribers on one target): a guard that only compares the batch's end with the checkpoint applies its first part twice, so the target filters by its checkpoint. `cursors` and `target` together throw `UsageError`. New: `CheckpointTarget`, `Subscription.watermark`, `Subscription.hasPassed`, `QueryResult.watermark`, `AppendResult.transactionId`.

### Typed read model definitions

- **Typed read model definitions and reads: `keyBy`, `where` and `sort.by` are checked and completed by the compiler.** `registry.$filter(...)` now returns a `Filter` whose type remembers the registry and the chosen types (`$filter<const N>(filter?: RegistryFilter<D, N>)`; the remembered part is an optional, type-only property — the returned object is unchanged, stays assignable to `Filter`, `Filter[]` and `Query`, and a plain `Filter` still fits a variable inferred from it; `RegistryFilter` gains a defaulted second type parameter). With such a source, `defineReadModel`'s `keyBy` accepts only a scope key that one of the chosen event types declares (`scopes` or `optionalScopes`) or a chosen type's own id key (its `idKey`, else `<lowerFirst(Type)>Id`): a typo is a compile error instead of an empty model, editors list the keys, and a widened `string` is refused (`as const` on a `keyBy` held in a variable). `ListOptions<S>` is generic: on `list` and `watchList` of live and persisted models, `where` takes the state's fields `where` can compare (strings, numbers, booleans, `null`) with each field's own type — a literal union stays one; `Date`, array and object fields are not offered — and `sort.by` takes any field of the state. A source that is not a `$filter(...)` result (a `Filter` literal, `scope()`, `$scope()`, a `Query` variable, an array holding one) keeps `keyBy` a plain string; a state typed `any`, `unknown` or `Record<string, …>` keeps plain strings for `where` and `sort.by`. Types only: the built JavaScript is the previous commit's (compared file by file, chunk names aside). **Breaking (types of this unreleased branch):** a typed model handle is no longer assignable to `LiveReadModel<unknown>` / `PersistedReadModel<unknown>` — its `list` would then accept any field; type a collection of handles with `<any>`. A `where` object held in a variable needs `as const`, and a request value must be narrowed to the field's type.

  ```ts
  const byOffer = defineReadModel({ name: "offers", version: 1, source: sales.$filter(), keyBy: "offerId", initial: (): Offer => ({ status: "draft", amount: 0 }), fold });
  // @ts-expect-error a typo in keyBy is a compile error
  defineReadModel({ name: "offers-typo", version: 1, source: sales.$filter(), keyBy: "offerID", initial: (): Offer => ({ status: "draft", amount: 0 }), fold });
  const page = await es.readModel(byOffer).list({ where: { status: "open" }, sort: { by: "amount", dir: "desc" } });
  ```

### Other

- **`contextCache.onLoad`: what each context load cost.** Read time, fold time and sizing time per load, with events folded, cache hit, state bytes, query, tenant and an optional `name` on `es.context()` / `es.command()`. Shows whether a slow command waits on the database or computes in its fold. New type: `ContextLoad`.

## 0.6.4 (2026-09-30)

- **An initial factory written inline missed the cache on every call.** 0.6.3 keyed `initial: () => …` by reference, and an inline arrow is a new function each time, so stable folds with an inline factory never hit. A factory is now keyed by its source text: the same factory starts the same state, a different one does not. Folds stay keyed by reference — two folds must never share a state; define a fold once (module level) to keep it cached.

## 0.6.3 (2026-09-30)

- **Fix: two folds over one query shared one cached state.** The context cache keyed only by the query, so `es.context()` / `es.command()` with the same query but a different `fold` (or a different `initial`) got the other fold's state — a command could decide on it, and `appendIf` let it through because the context version matched. The key is now query + fold + initial state: folds and non-plain values by reference, plain values by content (bigint, NaN, -0, undefined, cycles and very deep values handled; beyond 64 levels or 10 000 nodes by reference). A plain `initial` is copied on a cold load, so a fold that updates its state in place never changes the caller's object. `invalidate(query)` forgets the query under every fold. Define folds once (module level): a fold created per call is correct, but never hits the cache.
- **Fix: `estimateSize` overflowed the call stack on a deeply nested state** — it now walks with an explicit stack.
- `ContextTooLargeError` names the query again, not an internal cache key.
- Example: the in-memory search index kept a durable file cursor, so after a restart it skipped everything the lost index had held; a cursor now lives where its projection lives.

## 0.6.2 (2026-09-29)

Live streams of large events were expensive: measured, one 424 kB event waiting on an older transaction travelled to the app about six times a second, per watch group.

- **Fix: `subscribe` and `watch` fetch every record once.** Since 0.5.0 a woken reader also fetched the unsettled tail — full payloads, up to a batch — and fetched it again every 25–500 ms until an older transaction ended. It now reads settled records only; when that page is empty, one row beyond the cursor without its payload (`payload: false, limit: 1`, from the transaction index) tells whether something waits. Measured on the same case, 2.5 MB/s became under 0.1 MB for the whole wait, and a waiting event after a sequence/transaction inversion still arrives within half a second.
- **The cursor read uses the `(transaction_id, sequence_number)` index.** Its condition was a `NOT` over an `AND`, which no index serves, so every read beyond a cursor walked every row of the query (the whole tenant, for a relay); it is now the equivalent two index ranges.
- **Lean reads:** `QueryOptions.data: false` (`scopes`, the own id whatever its key, and declared scope keys carried flat stay; no top-level string over 1 kB and nothing else of the payload leaves the database; a payload that is not an object reads as empty), `payload: false` (the payload column is not read at all), `version: false` (no context version; `-1`, never guards). `subscribe` and `watch` take `data: false` and `payload: false`; a lean and a full watcher never share a reader. `es.read` refuses both.
- **Many scope values:** the read-path version check turns more than eight values of the leading key into one `MAX … IN (…)` instead of a `UNION ALL` branch per value (planning time grew with every value); a read may list up to 10 000 values per key, a guard stays at 256 (each is a lock) and gets a clear `UsageError` beyond.
- **`ANALYZE` after an install that created statistics objects**, after its COMMIT — so it holds neither the install lock nor a DDL lock (with large payloads it takes seconds) — best-effort, a warning when it fails. A new object is empty until the table is analysed (after an adoption, say), and the planner misjudged the scope indexes until autovacuum came by.

## 0.6.1 (2026-09-29)

- **A view stayed broken after its store failed once at first use.** The root api reset its store promise on a failed creation, but every view — the root api's own and every tenant view — kept the first rejected promise, so one transient database error on first use (the database not up yet, a failed install) failed that view's reads and writes until the process restarted. A view now tries again on its next call.

## 0.6.0 (2026-09-28)

- **`postgres: { adopt }` takes an existing events table over at install**, in place: `adopt: { columns: { sequence: "id", type: "eventtype" } }` renames the legacy columns, adds `metadata` and `transaction_id` (legacy rows get `adopt.legacyTransactionId`, default `3`, so they sort before every new row), makes `sequence_number` unique when it is not, then installs as always. Metadata-only — no row rewritten, `payload` never touched — inside the install transaction under the install lock, with row count and highest sequence compared before and after; idempotent on every later boot. A table that does not fit (half adopted, `json` payload, `integer` sequence, NULLs — also in the sequence column —, a `NOT NULL` column without a default, one column named for two roles, a `legacyTransactionId` not below every running transaction, under `rls` a foreign permissive policy) stops the install before anything changes; the adoption's reads run with `row_security = off`, so they never count a filtered table. Legacy indexes, columns, triggers, restrictive policies and write grants are kept and listed in `warnings()`. `mode: "check"` fails the install with the plan instead (also when the table is missing); `requireExisting` refuses to create a missing table; `store.adoptionPlan()` reads the plan, `printAdoptSql({ plan })` prints it. New: `planAdoption`, `adoptStatements` and their types.

## 0.5.0 (2026-09-28)

Live pushes across processes, with hard limits instead of options.

- **`es.subscribe(name, query, handler, options?)`** and **`es.watch(query, handler, options?)`** on the api, next to `append`: both read through the view they are called on (a tenant view: that tenant only, under its session). `subscribe` is durable (named cursor, `name@tenantId` on a tenant view, at-least-once); `watch` is ephemeral (from about now, at-most-once) and shares one reader per view and query in the process. A watcher that falls `watch.maxPendingBatches` (64) behind is dropped with the new `WatchOverflowError`; `watch.maxWatchers` (10 000) caps them per process. Past views (`asOf`) refuse both.
- **The commit doorbell on Postgres: `postgres: { live: true }`** installs a statement trigger that `pg_notify`s after every insert statement on commit with an **empty payload** — no sequence, tenant, type, scope or data — and one `LISTEN` connection per store (`live: { connection }` for a direct one behind PgBouncer). New optional store capability `WakeStore` (`onCommitted`), implemented by both stores and passed through tenant views; `subscribe` wakes on it (doorbells within 25 ms share one read, and never cut a retry back-off short), re-reads soon while events wait on an older transaction, and polls only as a safety net (5 s). The listener reconnects with back-off and wakes everyone once after every (re)connect; without the trigger it warns and wakes every 500 ms. `watch` takes an `AbortSignal`, ends on store errors no retry will fix, and `es.close()` ends every watch. New: `notifyChannel`, `notifyFunctionDdl`, `notifyTriggerDdl`, `isWakeStore`, and `PostgresStore.notificationQueueUsage()` for health checks — a listener that stays connected but stops reading fills the notification queue until notifying commits fail.
- **Fix: a subscription whose start position could not be loaded replayed everything.** When the cursor store (or the store, for `from: "now"`) failed at start, `subscribe` fell back to the beginning. It now retries resolving the start position like any failed poll.
- `NegatedFilter` (0.4.0) is now exported, as the 0.4.0 notes said.

## 0.4.0 (2026-09-28)

Two gaps a consumer migration ran into: a guard over a whole scope that leaves some facts out, and reading the store as it was.

- **`not` in a filter**: a filter or a list of filters whose matching records are left out of the rows and of the context version; `appendIf` re-checks exactly that. Locks come from the positive part only, a negated scope key need not be declared, a record lacking a negated key stays in. Nested `not`, an empty negation, and a `where` predicate inside `not` that is empty or holds `undefined` (it would turn into `{}` on the way to JSON and leave out the whole context, so its version would never move) are `UsageError`. New type `NegatedFilter`.
- **`es.asOf(sequence)`**: a read-only view of the store as it was at that event (inclusive). Reads, `read` and `context` see only records up to it, and their context version is computed within the cutoff; `append`, `appendIf`, `appendIfOrThrow` and `command` throw `UsageError`; nested views only narrow; no context cache; `statistics()` refused; a custom store that ignores `until` is refused instead of answering with the live state. `store()` stays the unrestricted escape hatch. Underneath: `QueryOptions.until`, which — unlike `after` and `cursor` — caps the context version too.
- **Postgres: the append function is now `es_append_if_v5`** (the version spec carries the negations). The installer creates it and drops `_v4`, as it did for every earlier version: a process still on 0.3 cannot append once a 0.4 process has installed. Roll out all processes together, or install by hand with `printSchemaSql()` and `install: "none"` and drop `_v4` after the rollout.

## 0.3.1 (2026-09-28)

- **A tenant view refused an event that names its tenant in `scopes` when the data carried another value under the tenant key.** The append check looked at the flat data field before `scopes`, while every read (`es_scope`, the memory store) lets `scopes` win. An event recorded in the platform tenant that announces a new tenant with its key as a top-level field (`scopes.tenantId = "system"`, `data.tenantId = "<new>"`) threw `TenantMismatchError`. Now `scopes` decides when it names the view's tenant; without it the flat field still decides, fail-closed. Reads were never affected.

## 0.3.0 (2026-09-28)

Two things a non-owner role under row-level security paid for on every read.

- **`LEAKPROOF` for the scope indexes under `rls`**: the installer marks `jsonb_typeof`, `jsonb_object_field` and `jsonb_object_field_text` `LEAKPROOF` when it runs as a superuser, otherwise it records a warning with the statements (`warnings()`). Without them Postgres may not use a scope index as an index condition for a non-owner role and filters every scope but the tenant over the whole tenant. New: `SCOPE_BUILTIN_FUNCTIONS`, `scopeLeakproofStatements()`, `SCOPE_LEAKPROOF_MISSING_SQL`; `printSchemaSql({ rls: true })` lists the statements.
- **`scopeStatistics`** (installer) and `DdlOptions.scopeStatistics` (static DDL): statistics objects only for the keys that need them. Every object costs planning time in every statement on the table; `{ minIndexRows, exclude }` keeps them where the scope index holds at least that many rows (`DEFAULT_SCOPE_STATISTICS_MIN_ROWS` = 1 000, measured) and drops the others. New: `scopeStatisticsKeys()`, `scopeIndexRowsSql()`; `scopeRebuildStatements()` takes the chosen keys. Default unchanged (`"all"`).

## 0.2.1 (2026-09-28)

- **`invalidate()` without a query released nothing from the process-wide budget.** It cleared the view's entries but left their bytes in `CacheBudget` as ghosts. Once a ghost was the oldest entry and the budget was exceeded, `CacheBudget.touch` evicted it again and again without freeing anything — a synchronous endless loop that blocked the event loop for every tenant. Affected: every `invalidate()` on a view or on the api, and the eviction of a tenant view from the `maxTenantViews` LRU. Now `invalidate()` releases each entry, and the budget drops a token itself when its cache no longer holds the entry.

## 0.2.0 (2026-09-15)

Two things applications had to do with raw SQL beside the package, now inside it. Both are reads; the store stays append-only. Deliberately still outside: cross-tenant directory functions and tenant erasure.

- **`omit`** on `query`/`read`: top-level `data` keys every returned record leaves out — a projection for lists that do not need a large field (an article body). The Postgres store strips them in SQL (`payload - '{…}'`), so the field never travels. `where` and `contextVersion` see the full record; `scopes` and the own id key are refused; `es.read` re-validates without the omitted keys and types `data` as `Omit<…>`. Decisions (`command`, `context`) have no `omit`.
- **`statistics(query?)`** on both stores, on the api and on tenant views (narrowed): count, stored bytes (`pg_column_size`, no payload fetched) and last sequence per event type.
- New optional capability interface `StatisticsStore`; `EventStore` is unchanged, so custom stores keep compiling. `TypeStatistics` and `TrimmedDataOf` exported.
- Operations: a recipe for erasing a tenant (the one write the package deliberately does not offer).

## 0.1.0 (2026-09-08)

First cut of `@orgops/eventstore`, built in one night from the research in `research/`. Every concept is the joint work of Ralf Westphal and Rico Fritzsche (event-orientation, Command Context Consistency, scoping events); this package is an implementation of it on PostgreSQL.

- **Core**: `defineEvents` (Zod v4) with typed creators, `$fold`/`$foldAll`, `$filter`/`$scope`, `$parse`; envelope rules (own id and `scopes` never inside `data`, string scope values); `configure()` + ambient `es`, `createEventStore()`; `es.command()` (read → decide → `appendIf`, retries on conflicts and transient failures with jittered back-off); `es.context()` incremental context cache over settled events with a gap-free `(transactionId, sequence)` cursor; `es.read(registry)` typed reads; tenant views (`forTenant`, `forPlatform`, fail-closed stamping, memoised per tenant); typed errors with `httpStatus`.
- **Postgres**: one `events` table; `es_scope()` inlinable expression function; one B-tree per declared scope key with `CREATE STATISTICS`; partial unique indexes per `unique` path; idempotency-key index (per tenant when a tenant key is configured); `es_append_if_v4` — advisory locks in one sorted pass (shared tenant stamps, exclusive scope pairs, shared/exclusive global), fresh-snapshot version check, batched `unnest` insert, READ COMMITTED enforced, `search_path` pinned, `EXECUTE` revoked from PUBLIC; fingerprinted installer under a transaction-scoped advisory lock; per-connection timeouts; transient-error mapping; optional RLS with per-transaction `set_config`.
- **Memory**: the semantic reference store with posting lists per type and per `(scopeKey, value)`; every candidate re-verified with the full predicate.
- **Subscribe**: durable, gap-free, at-least-once subscriptions with pluggable cursor stores (`memoryCursors`, `fileCursors`); in-process `on()` for live stores.
- **Testing**: shared conformance suite (runs against memory and Postgres), `given/when/then`, `interferingStore`/`slowStore`/`recordingStore`, `makeEvent`.

Measured on Docker Postgres 18 with 1.9 M events (see `research/30-journal.md`): 6 600 full commands/s at 16 clients (read + decide + guarded append), 10 600 context reads/s, 208 000 events/s in 50-event batches; 16 concurrent guarded appends on one context → exactly one commits. 163 tests: shared conformance suite against memory and Postgres, constructed xid/sequence inversions, deadlock schedules, RLS with a non-owner role, an end-to-end example app.
